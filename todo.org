* TODO Vorgehen für die Implementation mit =url-retrieve= und Callback

** Ziel
Für mehrere Dictionary-Sources (z. B. Duden, DWDS, OpenThesaurus, Wiktionary) sollen Requests *parallel* gestartet werden.  
Jede Source implementiert dieselbe öffentliche API und liefert das Resultat in einem gemeinsamen plist-Format zurück.

Die Argumente und internen Bezeichner bleiben auf Englisch, auch wenn das Package sonst deutsch ist.

** Empfohlene Architektur

*** Dateien

- =woerterbuch-core.el=
- =woerterbuch.el=
- =woerterbuch-duden.el=
- =woerterbuch-dwds.el=
- =woerterbuch-openthesaurus.el=
- =woerterbuch-wiktionary.el=

*** Verantwortlichkeiten

**** =woerterbuch-core.el=
Gemeinsame Hilfsfunktionen:
- section handling
- common result helpers
- buffer/header helpers
- optional error/result constructors

**** =woerterbuch-<source>.el=
Jeweils Source-spezifisch:
- URL building
- HTTP request via =url-retrieve=
- parsing of HTML or JSON
- extraction of requested sections
- returning a normalized plist result

**** =woerterbuch.el=
Aggregator:
- starts all source requests in parallel
- collects all results
- calls one final callback when all requests are complete

** Öffentliche API pro Source

Jede Source sollte genau eine einheitliche Fetch-Funktion exportieren:

#+begin_src elisp
(woerterbuch-<source>-fetch word sections callback)
#+end_src

*** Argumente
- =word=: String, der gesucht wird
- =sections=: Liste der gewünschten Bereiche, z. B.
  - =(:definitions :synonyms)=
  - =(:definitions :synonyms :origin :idioms)=
- =callback=: Funktion, die genau *ein* normalisiertes Ergebnis entgegennimmt

*** Beispiel
#+begin_src elisp
(woerterbuch-openthesaurus-fetch
 "Baum"
 '(:synonyms)
 callback)
#+end_src

** Gemeinsames Result-Format

Jede Source sollte dieselbe Struktur zurückgeben.

*** Erfolgsfall
#+begin_src elisp
(:source openthesaurus
 :word "Baum"
 :ok t
 :definitions nil
 :synonyms ("Makrophanerophyt" "Baumstruktur")
 :origin nil
 :idioms nil)
#+end_src

*** Fehlerfall
#+begin_src elisp
(:source dwds
 :word "Baum"
 :ok nil
 :error "HTTP error")
#+end_src

*** Warum dieses Format?
- alle Backends sind gleich konsumierbar
- Aggregator und UI müssen nicht source-spezifisch verzweigen
- fehlende Daten können einfach =nil= sein
- spätere Merge-Logik wird deutlich einfacher

** Rolle des Callback

Der Callback ist die Funktion, die aufgerufen wird, *nachdem* der Request fertig ist.

Bei =url-retrieve= läuft das typischerweise so:

1. Request wird gestartet
2. Emacs arbeitet normal weiter
3. wenn die Antwort eintrifft, ruft Emacs deinen Request-Callback auf
4. in diesem Callback:
   - prüfst du =status=
   - springst hinter die HTTP-Header
   - parsest JSON oder HTML
   - extrahierst die gewünschten =sections=
   - baust ein einheitliches plist-Result
   - rufst den übergeordneten =callback= mit diesem Result auf

** Typischer Ablauf je Source

*** Schritt 1: öffentliche Fetch-Funktion
Die öffentliche Funktion:
- baut die URL
- setzt Header
- startet =url-retrieve=
- übergibt =word=, =sections= und =callback= an den internen Request-Callback

#+begin_src elisp
(defun woerterbuch-openthesaurus-fetch (word sections callback)
  "Fetch WORD from OpenThesaurus asynchronously."
  (let ((url-request-extra-headers
         '(("User-Agent" . "woerterbuch/0.1 (contact: you@example.com)"))))
    (url-retrieve
     (woerterbuch-openthesaurus--build-url word sections)
     #'woerterbuch-openthesaurus--request-callback
     (list word sections callback)
     t
     t)))
#+end_src

*** Schritt 2: interner Request-Callback
Dieser Callback wird von =url-retrieve= aufgerufen.

Wichtig:
- der aktuelle Buffer ist der Response-Buffer
- =status= enthält Request-Informationen und Fehler
- am Ende sollte der Buffer wieder freigegeben werden

#+begin_src elisp
(defun woerterbuch-openthesaurus--request-callback (status word sections callback)
  "Handle async response for WORD."
  (let (result)
    (unwind-protect
        (setq result
              (if (plist-get status :error)
                  (list :source 'openthesaurus
                        :word word
                        :ok nil
                        :error (format "%S" (plist-get status :error)))
                (woerterbuch-openthesaurus--parse-response word sections)))
      (kill-buffer (current-buffer)))
    (funcall callback result)))
#+end_src

*** Schritt 3: Response parsen
In der Parse-Funktion:
- HTTP-Header überspringen
- JSON oder HTML parsen
- nur die angeforderten =sections= extrahieren
- Ergebnis als plist zurückgeben

Beispiel für JSON:

#+begin_src elisp
(defun woerterbuch-openthesaurus--parse-response (word sections)
  "Parse current response buffer for WORD and SECTIONS."
  (goto-char (point-min))
  (re-search-forward "^$" nil t)
  (forward-char 1)
  (let* ((json-object-type 'alist)
         (json-array-type 'list)
         (data (json-read))
         (result (list :source 'openthesaurus
                       :word word
                       :ok t)))
    (when (memq :synonyms sections)
      (setq result
            (plist-put result :synonyms
                       (woerterbuch-openthesaurus--extract-synonyms data word))))
    result))
#+end_src

** Nur gewünschte Sections extrahieren

Statt immer alles zu parsen und aufzubereiten, sollte jede Source nur die angeforderten Bereiche extrahieren.

*** Beispiel
#+begin_src elisp
(when (memq :synonyms sections)
  ...)

(when (memq :definitions sections)
  ...)

(when (memq :origin sections)
  ...)

(when (memq :idioms sections)
  ...)
#+end_src

*** Warum?
- weniger unnötige Nachbearbeitung
- klarere Parser
- kleinere Result-Strukturen
- UI kann sehr gezielt arbeiten

** Aggregator für parallele Requests

Der Aggregator startet alle Sources gleichzeitig und sammelt die Resultate.

*** Öffentliche Funktion
#+begin_src elisp
(woerterbuch-fetch-all word sections final-callback)
#+end_src

*** Beispiel
#+begin_src elisp
(defun woerterbuch-fetch-all (word sections final-callback)
  "Fetch WORD from all configured backends in parallel."
  (let* ((fetchers (list #'woerterbuch-duden-fetch
                         #'woerterbuch-dwds-fetch
                         #'woerterbuch-openthesaurus-fetch
                         #'woerterbuch-wiktionary-fetch))
         (pending (length fetchers))
         (results nil))
    (dolist (fetcher fetchers)
      (funcall
       fetcher
       word
       sections
       (lambda (result)
         (push result results)
         (setq pending (1- pending))
         (when (zerop pending)
           (funcall final-callback (nreverse results))))))))
#+end_src

*** Rolle von =final-callback=
Der =final-callback= wird *einmal* aufgerufen, wenn alle parallelen Requests fertig sind.

Beispiel:

#+begin_src elisp
(woerterbuch-fetch-all
 "Baum"
 '(:definitions :synonyms :origin :idioms)
 (lambda (results)
   (message "%S" results)))
#+end_src

** Wichtige Implementationsregeln

*** 1. =lexical-binding= aktivieren
Ganz oben in jede Datei:

#+begin_src elisp
;;; -*- lexical-binding: t; -*-
#+end_src

Das ist wichtig, damit =word=, =sections= und =callback= sauber in Lambdas gebunden bleiben.

*** 2. Einheitliche Argumentnamen
Empfohlen:
- =word=
- =sections=
- =callback=
- =final-callback=
- =status=
- =result=
- =results=
- =fetcher=
- =pending=

*** 3. Einheitliche Section-Namen
Empfohlen:
- =:definitions=
- =:synonyms=
- =:origin=
- =:idioms=

Optional später:
- =:examples=
- =:pronunciation=
- =:etymology=

Falls Beispiele immer an Bedeutungen hängen, können sie direkt in =:definitions= enthalten sein.

*** 4. Einheitliche Source-Namen
Als Symbole:
- =duden=
- =dwds=
- =openthesaurus=
- =wiktionary=

*** 5. Buffer immer freigeben
Bei =url-retrieve= immer mit =unwind-protect= arbeiten und danach den Buffer schließen.

*** 6. Immer Fehlerfälle behandeln
Nicht nur Erfolg parsen, sondern auch:
- Netzwerkfehler
- Parserfehler
- leere Antwort
- unerwartete Struktur

** Empfohlenes Datenmodell für =:definitions=

Wenn Bedeutungen Beispiele enthalten sollen:

#+begin_src elisp
:definitions
'((:text "mehrjährige holzige Pflanze mit Stamm"
   :examples ("unter einem Baum sitzen"
              "der Baum ist alt"))
  (:text "azyklischer zusammenhängender Graph"
   :examples nil))
#+end_src

So bleiben Bedeutungen und Beispiele logisch zusammen.
